# 2026-09-17

## Mist re-tuned: "thick like vomiting" → fine aerosol haze

The user reported the Ritual spray read as a heavy solid lump, not a mist. Root cause
was the tuning of the GPU projectile shader (`BottleMist.tsx` + `useMistPhysics.ts`),
which had been dialled for *volume* on a previous request and never rebalanced for
*delicacy*:

- Droplets were clamped to 16px and `dotSize 0.12` hit that ceiling almost always,
  so every droplet rendered as a fat disc.
- Peak opacity `0.88` x per-particle `0.95` — heavy accumulation.
- 16° cone with low drag kept every droplet bunched in one tight beam.
- A hard `pos.y = min(0.0, pos.y)` clamp flattened the plume's top edge into a
  single sheet that then fell as one mass.

Rebalanced in the direction of "many particles, each tiny and faint, widely spread":

| constant | was | now |
|---|---|---|
| `count` | 1200 | 1500 |
| `dotSize` | 0.12 | 0.06 |
| point-size clamp | 3–16 px | 2–8 px |
| `peakOpacity` (new field, was hardcoded 0.88 in 3 places) | 0.88 | 0.45 |
| `coneAngle` | 0.28 (~16°) | 0.38 (~22°) |
| `drag` | 2.2 | 2.8 |
| `exitVelocity` | 2.4 | 2.0 |
| `gravity` | 1.4 | 1.6 |
| `particleLifetime` | 0.90 | 0.78 |
| per-particle alpha multiplier | 0.95 | 0.5 |
| age expansion | 1.0 + 1.1 | 1.0 + 0.55 |
| fade-out window | 0.35–1.0 | 0.16–0.8 |

Also allowed a small loft (`dir.y` capped at 0.08 in buffer generation, matching
`pos.y = min(0.08, pos.y)` in the vertex shader) so the plume has volume instead of a
flat top, and raised turbulence amplitude (0.04+r*0.04 → 0.05+r*0.06) so the beam
breaks into drifting wisps.

`MIST_OPACITY` is now sourced from `MIST_PHYSICS.peakOpacity` rather than duplicated —
the GSAP fade in `useBottleUncap.ts`, the shader uniform and the autonomous fallback
in `useMistPhysics.ts` all read the same number now.

Verified: `tsc --noEmit` clean, ESLint clean on both files, and a numeric simulation
of the shader kinematics confirms a diffused plume (forward reach ~0.5 units against
a ~2.4-unit bottle, ~0.23 units of downward droop by mid-life, peak per-droplet alpha
~0.19). **Not** browser-verified — this model cannot read images, so the screenshot the
user sent could not be inspected; the tuning is reasoned from the shader math and the
described symptom. The user needs to look at it in the browser (dev server is up on
:3000). If it is now too faint, `peakOpacity` is the single lever.

## Second pass: "barely visible" — the real cause was foreshortening, not opacity

The user reported the mist was now barely visible and asked to rotate the bottle right
before spraying. Re-checking the geometry showed the opacity cut was only half the
story — the *pose* was the other half:

The plume's axis is the nozzle's local +Z, and the Ritual tilt held the bottle at a
dead-front `y: 0` through the whole spray. Shooting straight down a 24° lens at a
camera 7.2 units away, the cloud's entire forward travel (~0.5 units) projects to
**x = 0** — the trajectory was invisible, and only the ~0.11-unit lateral halo gave
the cloud any screen width. A correctly-tuned mist still read as a faint blob for the
same reason a flashlight pointed at you looks like a disc.

Added `RITUAL_YAW = 0.4` (~23°) to `BottleScene.tsx` — a three-quarter turn toward the
viewer's right, settled over 2.0 -> 2.9 screens so it is in place *before* the pump
fires at 3.0, held through 4.5, then easing into the existing showcase pose (whose
`y: 0.35` is nearly the same yaw, so that transition is now mostly the x/z tilt).
The model and the mist are both children of the tilt group, so they yaw together:
the plume axis stays aligned with the nozzle and the origin-lock keeps the cloud
glued to the orifice. Gravity is re-projected into local space per frame and a pure
Y rotation leaves `(0, -1, 0)` unchanged, so droplets still fall straight down.

Modest visibility recovery to go with the now-legible profile view:
`peakOpacity` 0.45 -> 0.55, per-droplet alpha x0.5 -> x0.6, `exitVelocity`
2.0 -> 2.2. Deliberately kept well below the old 0.88/x0.95 — the profile view makes
the cloud optically deeper (more droplets along the line of sight), so the same
number reads denser than it did head-on.

Still not browser-verified. `RITUAL_YAW` is the lever if the turn reads as too much or
too little.

## Third pass: more yaw, longer plume, genuinely thin

Three asks in one: bottle further right, longer mist, and still too thick. The third
was the interesting one — the plume was still a *beam*, and a beam is dense by
construction regardless of droplet alpha, because the droplets all occupy a narrow
solid angle. The fix was to widen the cone faster than the length grew, so density
per unit volume falls even as reach rises.

| constant | was | now |

| `exitVelocity` | 2.2 | 3.1 |

| `coneAngle` | 0.38 (~22°) | 0.52 (~30°) |
| `count` | 1500 | 1100 |
| `dotSize` | 0.06 | 0.042 (clamp 2-8px -> 1.5-5px) |
| per-particle alpha | x0.6 | x0.42 |

The metric that mattered is **spread-to-length**: 0.51 -> 0.64, while reach nearly
doubled (0.43 -> 0.80) and the visible arc tripled on screen (4.6% -> 13.9% of
half-viewport). Droplets fewer and smaller in a 52% wider cone — same haze, no rope.

`tsc` and ESLint clean. Still not browser-verified.

## Sixth pass: flatten the climb, double the length

The user said it was going too far *upward* and not reading like mist, and wanted the
projection roughly doubled. These pull in opposite directions via velocity alone —
raising velocity lengthens but also raises the apex.

First attempt lowered `elevationAngle` 0.40 -> 0.10 and eased drag to 1.1. Simulation
said the nominal on-axis droplet was flat (apex 0.072), but that number was misleading:
it described one droplet, not the cloud. Measured the **p95 apex across all droplets**
and found the real problem — the cone's upper edge launches at
`elevation + coneAngle`, so a 0.10 axis still fires the top edge at 0.62 rad (36 deg).
p95 apex was 0.73, and the previous config had been **1.37 units** — over half the
2.4-unit bottle. That was the jet the user saw, and no on-axis number would have surfaced it.

The fix was a **negative** elevation angle, aiming the axis slightly *downward* so the
cone's upper edge lands near level, paired with very low drag so droplets carry:

| constant | before this pass | now |
|---|---|---|
| `elevationAngle` | 0.10 | **-0.20** (aimed down ~11 deg) |
| `drag` | 1.1 | **0.55** |
| `exitVelocity` | 6.5 | 6.5 (held) |
| `particleLifetime` | 0.90 | 0.90 (held) |

Verified across the full cloud: p95 apex 1.37 -> **0.20** (nearly 7x flatter), mean
forward travel ~3.4 units (against ~2.56 at the config the user was looking at), and
**96% of droplets now finish their lifetime below the nozzle** — the "spread then
settle" silhouette of a real atomizer rather than a climbing jet. Length-to-height
ratio 17:1.

Lesson worth keeping: **tune particle systems on a percentile of the cloud, not the
nominal particle.** A cone's off-axis droplets behave nothing like its axis droplet,
and the on-axis number was actively hiding the defect the user was describing.

`tsc` and ESLint clean. Still not browser-verified.


## Fourth pass: the arc was structurally impossible

The user's reference image showed droplets spreading from the nozzle and then falling
under gravity. Checked the shader and found the arc could not happen at all — two
hard clamps forbade it:

1. `generateMistBuffers` had `if (dir.y > 0.0) { dir.y = 0.0; dir.normalize(); }` —
   every droplet was flattened to horizontal-or-down at birth.
2. The vertex shader had `pos.y = min(0.08, pos.y)` — any residual rise was clamped
   to a sliver regardless.
3. `elevationAngle: 0.0` — the plume axis was dead level.

Gravity had nothing to act against. The cloud could only ever sink, which is a hose,
not a spray. Removed both clamps and tilted the axis up by the elevation angle, so
gravity now spends each droplet's lifetime bringing it back down.

The shape then needed tuning so the arc *completes* rather than freezing mid-rise —
the first attempt (elevation 0.28, gravity 1.6) peaked at 0.35s but the droplet
evaporated at +0.02, still above the nozzle: the "then falls" half never happened.
Raised gravity and the lifetime together until the trajectory crosses back below the
orifice before fading.

| constant | was | now |
|---|---|---|
| `elevationAngle` | 0.28 (was 0.0 before that) | 0.40 (~23°) |
| `gravity` | 1.6 | 2.4 |
| `drag` | 2.2 | 2.0 |
| `particleLifetime` | 0.78 | 0.85 |

Verified numerically: 85% of droplets rise above the nozzle, 54% complete the full
rise-and-fall before fading (the rest dissipate mid-arc, which reads as natural
evaporation), mean peak height 0.16 units against a ~2.4-unit bottle, spread-to-length
ratio 0.76. The orthonormal basis in `generateMistBuffers` stays valid under the tilted
axis — `across` is still pure X, `up` tilts back to stay perpendicular.

`tsc` and ESLint clean. Still not browser-verified.

## The variant-change bug: mist invisible after switching bottles

"Only reveals when I restart the app; after changing the bottle the mist is not revealing
or may be invisible." Worked from code (cannot read images in this session — the `Read`
tool returns "model does not support reading images" — so everything was reasoned from
source and verified with Node simulations of the real three.js objects).

Ruled out first: the canvas is not remounted on variant change (`PersistentBottle` →
`BottleSceneMount` with an unkeyed `dynamic(..., { ssr: false })`), the refs object is
stable (`useMemo` over `useRef`s), and the variant switch is a plain `ScentProvider` state
update. `useBottleUncap`'s `useGSAP` deps are `[enabled, ready, trigger]`, none of which
change on a variant switch, so the Ritual controller persists.

The actual cause was in `BottleMist.tsx`: the uniforms memo **depended on `color`**,
`useMemo(() => createMistUniforms(color), [color])`, so every variant change built a
second uniforms object. R3F v9.7 does not hand a `ShaderMaterial` the object the prop
carries — `applyProps` *merges* it into a stable target (`Object.assign` per uniform,
"ShaderMaterial uniforms must keep a stable target reference"). Only the
`onUpdate={(mat) => { mat.uniforms = uniforms }}` shunt re-points the material afterwards,
and it is not guaranteed: `invalidateInstance` returns early while the instance has no
parent. In the branches where the shunt did not fire, the material kept rendering with
the object the per-frame writer in `useMistPhysics` had stopped updating; the merge had
already copied `uGlobalOpacity: 0` into it, and it stayed at 0 — invisible. On a fresh
load there is only ever one object, so nothing could diverge. That is exactly the
reported symptom and exactly why it was variant-correlated.

Fix — make the divergence structurally impossible: the memo is now
`useMemo(() => createMistUniforms("#322924"), [])`, one object for the component's life,
with the tint travelling through the existing `useEffect` that does
`uniforms.uColor.value.set(color)`. `diffProps` then never flags `uniforms` as changed, so
nothing down that path runs on a variant change at all. The `onUpdate` shunt is still
needed at *mount* (R3F's merge installs `{ ...uniform }` copies, not the real objects) but
is no longer load-bearing afterwards.

Also fixed `MIST_OPACITY` — it was still the hardcoded `0.88` while the tuning had moved
`peakOpacity` to `0.55`, so the GSAP fade on the scroll-driven path and the autonomous
fallback in `useMistPhysics` disagreed. It now derives from `MIST_PHYSICS.peakOpacity`.

Verified with a simulation transcribing R3F's exact `applyProps` / `invalidateInstance` /
`diffProps` / `is.equ` against a real `ShaderMaterial` (`scripts/mist-uniforms-test.mjs`):
with the old code and the shunt suppressed, `uGlobalOpacity` reaches the shader as `0`;
with the fix, writer and material share one object by construction. `tsc` and ESLint clean.

**Lesson worth keeping:** R3F keeps a `ShaderMaterial`'s `uniforms` object identity stable
and merges into it — never build a fresh one in a `useMemo` keyed on a prop, or the
per-frame writer and the renderer can silently hold different objects and the material
goes invisible with no error. And when tuning a cloud, measure percentiles of the whole
cloud, never the nominal particle.


## Seventh pass: rebuilt against a reference image

The user supplied a rendered reference and asked for the spray to look like it. Unlike
every earlier pass, **image reading worked in this session** (the model changed), so this
one was measured off the reference rather than reasoned blind. That is worth remembering:
the "cannot read images" limitation was model-specific, not permanent.

Measured off the reference, as fractions of the bottle height:
plume length 0.86, cloud diameter 0.585, cloud centre +0.057 above the orifice, cloud
bottom −0.236 below it, cone upper edge +32°, lower edge +7.4° (axis ≈ +20°, half-angle
≈ 12°). So the reference is: a **tight speckled cone** leaving the nozzle angled up ~20°,
which **balloons** into a broad soft cloud whose centre sits just above the orifice and
whose lower half hangs below it. Pale white against cream.

Wrote `scripts/mist-profile-sim.mjs` — the same dragged-kinematics simulation as before,
but **projected into screen space through `RITUAL_YAW`**, so its output is comparable to
the reference's measurements. That projection is the important part: the Ritual yaw
foreshortens the plume's forward travel to `sin(0.55) ≈ 0.52`, so a screen length of 0.86
bottle needs a *local* path of roughly double that. Tuning in local space against a screen
target would have come out half the intended length every time.

The two structural findings that drove the retune:
1. The old `elevationAngle: -0.20` with `gravity: 2.4` made the plume angle **down** on
   screen (−21.9°), not up. Gravity was overwhelming the elevation.
2. The old wide `coneAngle: 0.52` fattened the *nozzle* end. In the reference the cone is
   tight and only the cloud is wide — so the ballooning has to come from the turbulence
   amplitude (which the shader scales by `oneMinusExp`, i.e. it grows with droplet age),
   not from the launch angle. Raised the turbulence amplitude 0.05–0.11 → 0.20–0.42 for
   that, and kept the cone at 0.26.

| constant | was | now |
|---|---|---|
| `gravity` | 2.4 | 2.1 |
| `drag` | 0.55 | **1.1** |
| `exitVelocity` | 6.5 | 5.3 |
| `elevationAngle` | −0.20 | **+0.34** |
| `coneAngle` | 0.52 | **0.31** |
| `burstDuration` | 0.48 | 0.46 |
| `particleLifetime` | 0.90 | 0.92 |
| `count` | 1100 | 1500 |
| `dotSize` | 0.042 | 0.038 |
| `peakOpacity` | 0.55 | **0.42** |
| turbulence amp | 0.05–0.11 | **0.28–0.54** |

Shader: expansion `1 + 0.55·smoothstep(0,0.7)` → `1 + 1.05·smoothstep(0.15,0.85)` (the far
cloud grows rather than being a held shape); `fadeOut` from `smoothstep(0.16,0.8)` →
`smoothstep(0.30,0.95)` (the old fade dissolved the cloud before it formed — part of why
the far end read as a rope); halo weight 0.55 → 0.68 with a wider falloff `exp(-5.2d)`;
point-size clamp max 5.0 → 7.0. **Colour `mix(vec3(0.24,0.21,0.18), uColor, 0.55)` →
`mix(vec3(0.87,0.855,0.83), uColor, 0.18)`** — the plume had been built from a dark warm
base so it would read against the parchment, and it did, as a *brown cloud*; the reference
is white. Page ground is `--paper: #f3ece0`.

Measured result (screen space): plume length **0.879** bottle (target 0.860), cloud centre
+0.045 (target +0.057), cloud bottom −0.176 (target −0.236), cloud diameter 0.443 (target
0.585), axis +9.7° (target +19.7°). The two shortfalls — cloud diameter and cloud bottom —

position-only simulation cannot see; if the cloud still reads small on screen, those are
the levers, not the physics. The near-field "cone edge" figures (57.6° half-angle) are a
foreshortening artifact, not a real discrepancy: at small screen-x the yaw exaggerates the
angle, and the reference is full-profile while this view is three-quarter.

`tsc` and ESLint clean. Still not browser-verified.


## Eighth pass: the pale mist was invisible and the angle was read wrong

Feedback: "the Mist is barely visible and going too much opwords". Both were self-inflicted
in the seventh pass, and the second one was a measurement error on my side.

**The angle.** I had been reporting the *local* `elevationAngle` (0.34 rad = 19.5°) and
comparing it to a figure measured off the reference. But the Ritual yaw compresses the
plume's forward travel to `sin(0.55) ≈ 0.52`, which makes the angle the eye reads
`atan(tan(elevation) / sin(RITUAL_YAW))` — **very nearly double**. 0.34 local presents as
**34° on screen**. That is the climbing the user was seeing, and my simulation's "axis
angle" line had been averaging the upper and lower envelope edges (67° and −48°), which
happens to land near zero and hid it completely. Added an `apparent axis` line to
`mist-profile-sim.mjs` that computes it directly. **Anything above ~0.20 local reads as a
jet.**

`elevationAngle` 0.34 → **0.13** (≈14° apparent), and `gravity` 2.1 → 1.4 to match, so the
cloud settles back to about the orifice instead of being pulled below it.

**The visibility.** The seventh pass made two reductions at once — colour 0.24 → 0.87 and
`peakOpacity` 0.55 → 0.42, plus `dotSize` 0.042 → 0.038 — and the result was invisible.
The colour was the fatal one: the parchment is `--paper: #f3ece0`, already 0.95 in red, so
a white-ish mist can only sit ~8% below the page, under the threshold anyone notices. A
pale cloud cannot be pale *and* present on a 0.95 ground. The reference gets away with a
white spray because its background is a flat illustration, not a composited page.

| constant | was | now |
|---|---|---|
| `elevationAngle` | 0.34 | **0.13** |
| `gravity` | 2.1 | **1.4** |
| `dotSize` | 0.038 | **0.045** |
| `peakOpacity` | 0.42 | **0.58** |

Fragment shader: colour `mix(vec3(0.87,0.855,0.83), uColor, 0.18)` →
`mix(vec3(0.66,0.64,0.61), uColor, 0.26)` (mid warm grey), multiplier 0.46 → 0.50.

Measured (screen space): apparent axis **14.0°** (was 34°), plume length 0.907 bottle,
cloud centre −0.069 (about level with the orifice), 42% of droplets finishing below the
nozzle.

**Two traps hit again in this pass, both worth remembering:**
1. **Backticks inside a GLSL comment break the template literal.** `BottleMist`'s shaders
   are `/* glsl */ \`...\`` template literals, so a backtick-quoted token in a comment ends
   the string — `tsc` reported `TS1005: ',' expected` at the comment's line. Twice now.
   Never use backticks in shader comments; plain text or quotes only.
2. Measuring an envelope as `(upperEdge + lowerEdge) / 2` is not an axis. It landed on
   ≈0° while the axis was really at 34°, and it hid the defect the user could see.

`tsc` and ESLint clean. Still not browser-verified.

## Tenth pass: the cap flapped when re-entering the Ritual from below

Report: "when i scroll from Gallery to Ritual and then scroll down to the Gallery the Cap
just open and close in a very short frame". Gallery sits *below* the Ritual, so this is:
scroll up into the Ritual, then back down past it — a pass that never uncapped.

Cause, in `useBottleUncap`'s zone ladder. Zone 3's close is gated on `hasUncapped`:

```ts
if (screen >= CLOSE_FROM && isScrollingDown) { closeRequested = true; if (sprayDone) applyClose(); }
```

but `applyClose` places the cap on an **absolute** curve —
`baseCapY + height * LIFT * (1 - closeProgress)` — which at `closeProgress` 0 (i.e. exactly
`CLOSE_FROM`) is *fully open*. `hasUncapped` only clears below 2.5 screens, so it is still
true from the customer's earlier pass down to the Gallery. Scrolling back up into the
Ritual and down again therefore re-entered the close window with a **seated** cap, and the
close snapped it open on the way to shutting it: a flap with no spray behind it.

Fix: a new `capLifted` flag — "the cap is off the bottle right now, and owed a close" — set
in Zone 2 when the lift tween starts, cleared in Zone 1's reset, in `applyClose` once the
cap is fully shut, in `settleAfterSpray` when it seats, and in Zone 3's upward branch. The
downward branch now reads `screen >= CLOSE_FROM && isScrollingDown && capLifted`.

Confirmed with `scripts/uncap-state-sim.mjs`, a plain state-machine transcription of the
zone ladder driven by the reported scroll sequence. Current code: `OPENED-BY-CLOSE at screen
3.92: cap jumped 0 -> 0.98`. With the fix: no spurious opening.

**The generalisable lesson:** a controller that writes an *absolute* transform (position on
a curve) must be gated on the object actually being in the state that curve assumes — not on
a broader "we are past this point in the sequence" flag. `hasUncapped` answers a different
question from "is the cap open", and conflating them is what produced the flap.

`tsc` and ESLint clean. Still not browser-verified.
